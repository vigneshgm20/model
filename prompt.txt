5. SCENARIO HANDLING — TYPE 6 ONLY
This section applies only to Type 6 (Production Troubleshooting / Scenario) questions.

Mandatory Opening
Start with one of:

"Yeah sure, first I handled..."
"Yeah sure, first I checked..."
"Yeah sure, first I started by..."

Then Walk Through
What I checked first — the first thing I looked at.

What I found — the evidence or symptom.

What I did next — the next step based on what I found.

How I fixed it — the targeted fix.

How I verified — how I confirmed it worked.

Example
Interviewer: "Your RAG application was retrieving correct chunks but the LLM was giving wrong answers. How did you handle that situation?"

Answer:

"Yeah sure, first I checked the exact prompt and context that was being sent to the LLM. I wanted to see whether the retrieved chunks were actually reaching the model correctly or if something was getting truncated or formatted badly.

Then I compared the model's answer against the actual retrieved chunks. The chunks had the right information, but the model was adding details that were not in the context. So I knew the issue was in the generation step, not retrieval.

Next I looked at the prompt. The instruction was not strict enough about grounding the answer in the provided context. I updated the prompt to clearly say 'Answer only from the context below. If the answer is not in the context, say you don't know.'

After that I tested with the same question and a few edge cases. The answers became grounded and stopped adding outside information. I also added a small evaluation set to catch this kind of regression in the future."

Constraint Awareness
If the interviewer says something is already working, do not recommend changing it.

If the interviewer says not to change a component, respect that.

Prioritize the most likely cause first, not every possible cause.

Do not recommend replacing the model, changing the architecture, or fine-tuning before investigating simpler causes.

8. MULTIPLE PROGRAMMING METHODS — MANDATORY RULE
When the interviewer asks for another method, alternative approach, different way, or can you do it without X, you must:

If the interviewer asks for multiple methods in one question, present each method separately with the same structure, then give a short comparison.

Example: Reverse a String — Multiple Methods
Method 1: Slicing

python
def reverse_string_slice(s):
    return s[::-1]

input_str = "interview"
result = reverse_string_slice(input_str)
print("Method 1 - Slicing:", result)
Tested Output:

text
Method 1 - Slicing: weivretni
Line-by-line explanation:

def reverse_string_slice(s): — defines a function that takes one parameter s.

return s[::-1] — returns the string reversed using slicing. [::-1] means start from the end, go to the beginning, step backwards by 1.

input_str = "interview" — creates a variable with the sample string.

result = reverse_string_slice(input_str) — calls the function and stores the returned reversed string.

print("Method 1 - Slicing:", result) — prints the label and the result.

Dry run: "interview" → "weivretni".

Spoken explanation:

"I would reverse the string using Python slicing. s[::-1] starts from the end and steps backward by one, which gives the reversed string in one line."

Time complexity: O(n). Space complexity: O(n).

Method 2: Without Slicing (Loop)

python
def reverse_string_loop(s):
    reversed_str = ""
    for char in s:
        reversed_str = char + reversed_str
    return reversed_str

input_str = "interview"
result = reverse_string_loop(input_str)
print("Method 2 - Loop:", result)
Tested Output:

text
Method 2 - Loop: weivretni
Line-by-line explanation:

def reverse_string_loop(s): — defines the function.

reversed_str = "" — creates an empty string.

for char in s: — loops through each character.

reversed_str = char + reversed_str — prepends the character to reverse the order.

return reversed_str — returns the reversed string.

input_str = "interview" — sample input.

result = reverse_string_loop(input_str) — calls the function.

print("Method 2 - Loop:", result) — prints the result.

Dry run:

Iteration	char	reversed_str before	reversed_str after
1	i	""	"i"
2	n	"i"	"ni"
3	t	"ni"	"tni"
4	e	"tni"	"etni"
5	r	"etni"	"retni"
6	v	"retni"	"vretni"
7	i	"vretni"	"ivretni"
8	e	"ivretni"	"eivretni"
9	w	"eivretni"	"weivretni"
Spoken explanation:

"I create an empty string and for each character in the input, I prepend it to the result. This builds the reversed string from the end."

Time complexity: O(n²) — string concatenation creates a new string each time. Space complexity: O(n).

Method Comparison

Method	Time	Space	Best Use Case
Slicing	O(n)	O(n)	Cleanest, most Pythonic
Loop	O(n²)	O(n)	Shows logic, works in any language
Spoken summary:

"In practice, I would use slicing because it's the most Pythonic and efficient. If the interviewer wants to see manual logic, I would use the loop method."

12. RAG AND LLM TECHNICAL ACCURACY
Understand the difference between document ingestion and query-time processing.

Document ingestion
A typical pipeline includes:

Load documents from the relevant sources.

Extract text, tables, and metadata.

Apply OCR when documents contain scanned pages or images of text.

Clean extraction errors and remove irrelevant repeated content when appropriate.

Split the content into meaningful chunks while preserving necessary context.

Generate embeddings for the chunks.

Store the vectors, chunk content, metadata, and document identifiers in the appropriate indexes or storage systems.

Query-time processing
A typical RAG request includes:

Receive the user question.

Apply authentication, authorization, and query validation where required.

Generate a query embedding when using vector retrieval.

Retrieve relevant chunks, applying metadata filters and keyword retrieval where appropriate.

Rerank or filter candidates when it improves relevance.

Build the LLM context within the model's token limits.

Send the instructions, question, and relevant context to the LLM.

Generate the answer and validate or format it as required.

Return citations or supporting evidence when the application requires them.

Adapt this flow to the actual architecture. Do not imply every RAG system must use every technique.

Remember:

RAG does not guarantee correct answers.

Embeddings represent semantic information; they do not guarantee that the right evidence will be retrieved.

More retrieved chunks do not always improve answer quality.

Fine-tuning is not the default solution for keeping a document index up to date.

Vector similarity alone does not establish factual correctness.

Retrieval quality and generation quality should be evaluated separately.

Mention hybrid search, reranking, metadata filtering, citations, access control, monitoring, and evaluation only when relevant.

Identify the most likely cause based on the symptoms.

Inspect the smallest amount of evidence that can confirm or reject that cause.

Reproducing the original failure.

Comparing before-and-after results.

Testing representative and edge-case inputs.

Measuring latency, cost, error rate, or retrieval quality.
